# The D3D12 backend

```
tf-cli --model <dir> --backend d3d12 --prompt "..."
```

A second `IGpuBackend` implementation in HLSL, beside the CUDA one. It exists to
reach AMD and Intel, and to open the door to DirectStorage - the real Windows
analogue of the `pread` path the Mac original was built around.

It needs no toolkit. `d3d12` and `dxgi` are in-box, and `dxc` ships with the
Windows SDK the project already requires, so this backend builds on a machine
with no CUDA installed at all.

## It produces the same answers

Not "similar" - the same. An 80-token greedy generation is byte-identical to
CUDA's, and all 38 kernel test cases run against **both** backends and the same
scalar CPU references:

```
tf_tests "[kernels]"    38 test cases, 20366 assertions, both backends
```

That is the whole reason `tests/gpu/Harness.h` parameterizes over
`compiledBackends()` rather than taking the first. A second backend checked by a
second suite written to match whatever it happens to do proves nothing; checked
by the tests that already pin CUDA against a CPU reference, a disagreement
cannot hide.

## Speed, honestly

RTX 5060 Ti, all resident, greedy:

| | Prefill | Decode |
|---|---|---|
| CUDA | 164 tok/s | 40.6 tok/s |
| D3D12 | 12.6 tok/s | 23.7 tok/s |

Decode is within about 1.7×. Prefill is 13× off, and the reason is specific
rather than mysterious: the CUDA GEMM reads its staged activations as `float4`
and carries four output rows per lane, while the HLSL version reads scalars from
a `ByteAddressBuffer` and gets no vectorization from it. Prefill is dominated by
that kernel; decode uses the GEMV, where the gap is much smaller.

There is also a full UAV barrier after every dispatch. CUDA gets its ordering
from the stream for free; here it has to be stated, and stating it
conservatively costs overlap. Tracking which buffers actually alias would
recover some of that - but a missed dependency produces numbers that are wrong
only sometimes, which is the worst failure this project has.

Neither is a reason to use D3D12 on an NVIDIA card. Both are worth fixing before
anyone runs this on hardware where D3D12 is the *only* option.

## What differs from CUDA, and why the interface survives it

**Command lists, not streams.** D3D12 records into a list and executes it as a
unit, so a `Stream` here buffers work and submits it at `synchronize()`. The
runtime already synchronizes where it matters - the router readback, the end of
a step - so the observable ordering is unchanged.

**Readbacks are two-step.** A device-to-host copy lands in a readback resource,
and only after the GPU finishes can it be memcpy'd to the caller. Those deferred
copies queue per stream and flush on synchronize, which is exactly where the
caller was going to wait.

**Root descriptors, no descriptor heap.** Every kernel argument is a raw buffer
address plus a few constants, and a root UAV costs two DWORDs of the 64
available. Descriptor tables would mean a heap, a ring allocator and lifetime
tracking for no benefit. A `DeviceView`'s offset folds into the root address, so
no shader takes an offset parameter.

**Wave width is read, not assumed.** NVIDIA is always 32; AMD's RDNA can be
either; Intel varies. Every place the width matters here is a stride, so
`WaveGetLaneCount()` suffices and no shader needs `[WaveSize(32)]`.

**`multiprocessorCount` stays zero.** It is a CUDA concept with no D3D12
equivalent, so the backend leaves it rather than guessing, and the test asserts
it only for CUDA.

## Two things that were wrong and are worth remembering

**HLSL's `tanh` is not accurate enough.** It is a driver-supplied approximation
with no specified accuracy, and it measured ~2.5e-5 of absolute error against
the CPU reference - which failed the elementwise tolerance on GeGLU outputs near
zero, where a small absolute error is a large relative one. `stableTanh` builds
it from `exp` instead: more accurate here, and identical on every driver.

**Storing a half needs an atomic.** Two adjacent threads writing adjacent
`half`s share a dword, so a read-modify-write races. The KV writer does exactly
that on every token, so `storeHalf` uses `InterlockedAnd`/`InterlockedOr` on the
packed word.

## Not done

- **DirectStorage.** The reason this backend is interesting for streaming, and
  not wired up. The expert streamer still reads through Win32 overlapped I/O
  into pinned memory, which works on both backends.
- **Vectorized GEMM loads**, which is where the prefill gap is.
- **Tested only on NVIDIA.** Every design choice here is portable by
  construction - runtime wave width, no vendor intrinsics, feature level 12_0 -
  but no AMD or Intel card has run it. That is the one claim this document
  cannot make.
